# 性能优化第三轮：增量汇总与磁盘缓存

先读 `AGENTS.md`、`docs/perf-cost-incremental.md`、`docs/perf-startup-round2.md`。不提交、不推送、不安装。工作区里有大量其他未提交改动，一律不碰、不回滚、不格式化。

## 0. 现状（真实 5 GB 会话目录实测）

- 第二轮后：启动 30 秒累计 CPU 42 s、6 分钟 81 s、内存峰值 553 MB。
- 已修复：`scanCodex` 以前按单次扫描窗口清缓存，30 天扫描与全历史扫描互相清空，每 5 分钟重解析全部历史（含压缩归档）。现在只清除已不存在的文件（`CostService.swift` 中 `existingPaths`），并有测试。
- 仍然存在：每 5 分钟（`MonitorRefreshCadence.cost`）费用刷新约 100% CPU、约 15 秒。采样显示主体是 `CostService.summarizeScope`、`usageTotals`、排序与字典查找——每次都对 30 天与全历史两批全部事件从头汇总。
- 每次启动都要重新解析整个会话目录（解析结果只在内存里）。

## 1. 汇总结果增量更新

目标：费用刷新时，若与上次相比只是在若干文件末尾追加了事件，就只把新增事件计入，不再全量重算。

- 以「文件路径 → 已计入的事件数」记录汇总所依据的事件集合。`cachedParseCodexFile` 的追加路径已知道新增事件；把新增事件交给汇总层。
- 以下任何情况必须回退全量重算，并有测试覆盖：文件被替换／截短（缓存重建）、文件被删除、`sessionPathOverrides` 或项目目录（`CodexProjectCatalog`）变化、账号上下文（`UsageAccountContext`）变化、日期跨天（窗口边界移动）、去重结果可能变化（新增事件与已有事件重复）、价格表（`PricingCatalog` / `OfficialPricingCatalog`）变化。
- 增量路径的输出必须与全量重算**逐项相等**。测试：随机生成多文件事件，交替追加与各种回退情形，每一步都比较增量结果与全量结果。
- 若某个汇总量（例如排名、分位数）无法安全增量，可以只对该部分全量计算，但要在报告中说明，并给出实测耗时。

## 2. 解析结果磁盘缓存

目标：重启 App 后不再重新解析整个会话目录。

- 位置：`~/Library/Caches/CodexNotchMonitor/cost-parse-cache-v1/`（用 `FileManager.urls(for: .cachesDirectory, ...)`；这是可再生缓存，不属于 AGENTS.md 保护的应用支持目录，也不得写入 `~/.codex`）。
- 内容：每个会话文件一项——路径、设备号与 inode、文件大小、修改时间、已解析偏移、解析状态（model / sessionID / projectPath）、事件列表（只存 `TokenUsageEvent` 的结构化数值字段，不存任何对话内容）。可按文件分片或单文件二进制（`PropertyListEncoder` 二进制或自定义紧凑格式均可），写入采用原子替换。
- 读取：启动时载入；标识、大小、修改时间与当前文件一致则直接使用；追加则从偏移增量解析；否则丢弃该项重新解析。缓存格式版本号不符、文件损坏或解码失败时整体丢弃，绝不能导致崩溃或错误数据。
- 写入时机：每次扫描结束后合并写入，节流（例如至少间隔 60 秒，App 退出时尽量写一次）；写入在后台队列进行。
- 大小控制：只保留当前仍存在的文件；在报告中给出用户真实目录下的缓存大小估算方法（测试中用合成数据）。
- 测试：冷启动解析 → 写缓存 → 新的 `CostService` 实例从缓存载入后不读取会话文件（读取计数为 0）且结果相同；追加后只读新增字节；缓存损坏／版本不符时安全回退；文件被替换时不使用旧缓存。
